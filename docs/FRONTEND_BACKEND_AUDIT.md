# Frontend-to-backend integration audit

25 November 2026. Baseline commit: `d067aa103ef5114e362be170e84182d8d3ea23e7`. Read all **137 page source files**, the API client and 72 route/dependency files. Selected authentication, settings, analytics and provider handlers were traced further. This is a source-level inventory, not exhaustive provider/backend acceptance or a claim that every imported component and service was verified.

**No page is certified production-ready by this inventory.** The coding executor is unavailable for this follow-up. New patches have not passed the Node test suite, Next build, MongoDB integration, browser or cloud E2E.

- **22 pages reference 81 distinct missing API-client methods.** Existing methods alone do not prove that their server routes are mounted, authorized or functional.
- **10 pages use optional API invocation.** Some missing mutation calls fall back to `{ success: true }` or otherwise continue without sending a request. These must be replaced by real operations and verified responses, not generic aliases or stub endpoints.
- **13 pages are static/state-seeded operational-content candidates.** This signal includes settings/catalog screens and needs semantic review; it does not mean every local UI state is a defect.
- The route parser extracted 367 Express/Next method/path declarations including 14 Next handlers. This is a structural candidate inventory, not proof of all mounted methods: dynamic declarations, nested/catch-all routes, middleware, ownership and execution must be reviewed explicitly.
- 25 server route files were not reached through the parsed main mounts. Do not blindly mount them: authentication, authorization, imports and real provider implementations need review first.

## Concrete root causes

1. `/env` uses global store actions and cannot reliably persist project secrets. The patch switches it to existing owned project env endpoints.
2. `/providers` seeds connected GitHub/Slack/Datadog records. The patch reads the server provider catalog and actual GitHub verification result.
3. Analytics overview/history return fixed metrics and random history from the controller. The patch queries actual owner-scoped deployment records and returns null for unavailable telemetry.
4. Authentication attaches `req.user._id` but multiple settings/provider controllers read `req.user.id`. The patch supplies both aliases from the verified identity and extends the existing identity regression assertion.
5. GitHub status deletes the integration record for any provider error, including transient/rate-limit failures. The patch preserves credentials on failed verification and distinguishes a 401 from a temporary outage.
6. Global `/settings` toggles are local and imply enforcement of deploy/security behaviors that is not established. The patch replaces them with navigation to specific settings.
7. Database user password generation uses `Math.random`. The patch uses browser cryptographic randomness with rejection sampling.

## Prepared implementation

| Page / component | Patch behavior | Acceptance still required |
| --- | --- | --- |
| `/env` | Load actual owned projects and variables; PUT/DELETE project keys; secret values masked; await server response before success | Tenant isolation, reload persistence, failure/stale states, secret redaction and real deployment env injection |
| `/providers` | Read provider catalog and verified GitHub status; no hardcoded connected accounts | Provider success/revocation/rate-limit tests and browser interaction |
| `/analytics` | Actual owner-scoped deployment counts/history, bounded 7/30/90-day UTC windows and honest unknown telemetry | MongoDB aggregation/index tests, account isolation and browser rendering |
| `/settings` | Navigation hub instead of unenforced global toggles | Linked settings still require their own implementation/acceptance; this does not certify them |
| `/databases/users` | Cryptographic generated password | Browser execution, DB user lifecycle and provider validation |
| Auth middleware | Canonical `id`, `_id`, `userId` refer to the same verified owner | Updated regression suite and all affected controller ownership cases |

The analytics service has isolated V8 syntax/logic checks with controlled storage for owner denial, bounded periods, query scope, observed counts and null telemetry. These are not Node/MongoDB/UI/cloud tests. New regression tests are prepared but have not run here. The previous 54-test result applies to the prior lifecycle commit, not this untested follow-up.

1. Identity, project selection, tenant boundaries and settings persistence. Fix incorrect principal aliases, legacy localStorage project assumptions and global-store mutations before enabling more admin/team surfaces.
2. Project/deployment/build/env pages: real queue/execution, stop/recovery, logs and failure contracts, full reload persistence and cross-owner denial.
3. Monitoring/analytics: actual collectors and ownership; unknown values stay unknown. Remove synthetic data from remaining services and prevent missing methods from becoming empty success.
4. Database pages: real provisioning, query/user management, backup/restore, migrations and scaling with provider jobs, permissions and measurable completion.
5. Domains/DNS/TLS, cron/functions/edge/media/forms/API/ISR: real isolated execution, storage, certificate and scheduler infrastructure. A CRUD record alone cannot enable these product capabilities.
6. Organizations/team/roles/invitations/SSO and advanced auth: organization authorization, delivery, actual protocol validation, revocation, MFA/session enforcement and audit events.
7. Billing/costs/payment methods: authoritative metering and provider-signed state, sandbox reconciliation and jurisdiction-supported merchant setup. Do not activate real charging from local UI state.
8. Remaining admin/compliance/security/integration pages: audited authorization and actual evidence/providers. No fake certification/uptime/savings/scan findings.
9. Resolve duplicate surfaces intentionally (backup/backups, invites/invitations, auth aliases). Preserve URL/query/token semantics and authorization boundaries; do not redirect sensitive token flows blindly.

For **each page**: identify exact operation → verify server mount/schema → implement owner/role scope → implement durable/provider operation → wire validated response → test loading/error/empty/stale states → test mutation failure and reload → test cross-tenant denial → perform real browser/provider acceptance. A disabled feature, a typed error, a static catalog or a generic request wrapper is not a completed backend feature.
